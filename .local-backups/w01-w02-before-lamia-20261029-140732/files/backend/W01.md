# W01 — authentification et profil personnel

Source : `docs/sprints/SPRINT 02.md`, S2-US1, S2-US2, S2-US3 et W01.

## État et activation

Logique d'inscription, BCrypt, sessions, profil, CSRF et CORS implémentée et testée
avec un `AccountStore` simulé. La persistance attend le script validé de Lamia.
Aucune entité JPA définitive, migration ou compte de secours n'est créé.
`fitness.auth.enabled=true` active les contrôleurs et exige un bean `AccountStore`.
Sans adaptateur, le démarrage échoue. Par défaut, les contrôleurs register/csrf/me
ne sont pas enregistrés. Les filtres login/logout sont configurés mais aucune
connexion ne peut réussir sans adaptateur. `ddl-auto=validate` reste inchangé.

## Validation

| Champ | Règles |
|---|---|
| email | String requise, strip puis minuscules Locale.ROOT, format email, maximum 254 unités UTF-16 |
| password | String requise non blanche, 12 à 64 unités UTF-16 ET maximum 72 octets UTF-8, aucun trim |
| displayName | String requise, strip, non blanche, 1 à 100 unités UTF-16 |

Les limites Java @Size comptent les unités UTF-16 : certains emoji en occupent deux.
L'email est normalisé aussi au login. Les champs inconnus, dont role, sont ignorés :
le serveur attribue exclusivement ADHERENT. Aucune donnée physiologique.
Ni mot de passe ni hash dans les réponses ; diagnostics des objets expurgés.
Le mot de passe du DTO d'entrée est également exclu de sa sérialisation JSON.

## Contrat API pour Meriem

Base : http://localhost:8080. Origine React autorisée : http://localhost:5173
exclusivement. Ne pas mélanger localhost et 127.0.0.1.
Tous les fetch doivent utiliser `credentials: 'include'`.

| Méthode et route | Corps / protection | Réponse nominale |
|---|---|---|
| GET /api/auth/csrf | Public ; conserve/crée une session | 200 jeton et headerName |
| POST /api/auth/register | JSON ; session et header CSRF | 201 profil ; ne connecte pas automatiquement |
| POST /api/auth/login | Formulaire HTTP ; session et header CSRF | 200 statut et session authentifiée |
| GET /api/me | Cookie de session authentifiée | 200 profil personnel |
| POST /api/auth/logout | Cookie et header CSRF courant | 204 sans corps |

### 1. Obtenir le jeton

```javascript
const response = await fetch('http://localhost:8080/api/auth/csrf', {
  credentials: 'include'
})
const csrf = await response.json()
```

```json
{"headerName":"X-CSRF-TOKEN","token":"<jeton opaque>"}
```

Le navigateur conserve JSESSIONID. Envoyer exactement le jeton reçu, sans le décoder.
Garder le jeton en mémoire côté interface et ne pas le journaliser. Il ne remplace
pas le cookie, n'est pas un jeton d'authentification et est lié à la session.

### 2. Inscription

```http
POST /api/auth/register
Content-Type: application/json
X-CSRF-TOKEN: <jeton reçu>
Cookie: JSESSIONID=<géré par le navigateur>

{"email":"a@example.test","password":"example-password","displayName":"Compte A"}
```

Réponse 201 :

```json
{"id":1,"email":"a@example.test","displayName":"Compte A"}
```

Ne connecte pas automatiquement. Appeler login ensuite. Aucun rôle ni ID à envoyer.

### 3. Connexion

```javascript
const response = await fetch('http://localhost:8080/api/auth/login', {
  method: 'POST',
  credentials: 'include',
  headers: {
    'Content-Type': 'application/x-www-form-urlencoded',
    [csrf.headerName]: csrf.token
  },
  body: new URLSearchParams({ email: 'a@example.test', password: 'example-password' })
})
```

Réponse 200 :

```json
{"status":"AUTHENTICATED"}
```

Le paramètre est email, pas username. Un JSON d'identifiants ne constitue pas une
connexion valide. L'identifiant de session change au login. Après succès,
rappeler GET /api/auth/csrf : l'ancien jeton n'est plus valide, puis charger /api/me.

### 4. Profil et rechargement

GET /api/me avec le cookie de session retourne 200 :

```json
{"id":1,"email":"a@example.test","displayName":"Compte A"}
```

L'identité vient de la session : un paramètre id ne change pas le profil.
Après rechargement de page : appeler /api/me pour reconnaître la session et
/api/auth/csrf avant une écriture. Ne pas simuler la connexion par localStorage.
Spring Security ajoute les en-têtes anti-cache aux réponses personnelles et CSRF.

### 5. Déconnexion et expiration

POST /api/auth/logout avec cookie et jeton renouvelé après login retourne 204
sans JSON. La session et le contexte sont invalidés, le cookie JSESSIONID supprimé.
Effacer profil et jeton en mémoire ; demander un nouveau CSRF avant de se reconnecter.
Sans session authentifiée ou après expiration, /api/me retourne 401 sans redirection
HTML : retirer les données personnelles affichées.

### Cookies et CORS

JSESSIONID est géré par le conteneur servlet, HttpOnly par défaut ; aucune lecture
ou écriture de ce cookie en JavaScript. Ne pas définir le header Cookie dans fetch.
En HTTPS, configurer `server.servlet.session.cookie.secure=true` ; ne pas l'imposer
à la démonstration HTTP locale. Durée et autres attributs suivent la configuration
Spring Boot du déploiement. Vérifier les vrais Set-Cookie sur serveur lancé :
MockMvc ne simule pas l'émission des cookies par un conteneur complet.

CORS autorise GET/POST, Content-Type, X-CSRF-TOKEN et les credentials.
OPTIONS de préflight est traité par le filtre CORS sans connexion.

| Situation | HTTP | Corps |
|---|---|---|
| Champs invalides/absents, JSON illisible | 400 | {"error":"INVALID_REGISTRATION"} |
| Email normalisé déjà utilisé | 409 | {"error":"EMAIL_ALREADY_USED"} |
| Email inconnu ou mauvais mot de passe au login | 401 | {"error":"INVALID_CREDENTIALS"} |
| Profil sans session ou compte indisponible | 401 | {"error":"UNAUTHENTICATED"} |
| CSRF absent/invalide | 403 | Réponse du filtre ; ne pas dépendre du texte |
| Origine/méthode/en-tête CORS refusé | 403 | Aucun JSON métier garanti |

Le navigateur peut présenter une erreur réseau CORS sans exposer le statut 403.
Un 403 CSRF doit conduire au renouvellement du jeton et à une décision explicite
pour retenter l'écriture. Ne pas réessayer automatiquement une inscription sans
vérifier son résultat. Méthode/Content-Type non prévus : 405 ou 415 possibles.

## Coordination PostgreSQL avec Lamia

Proposition antérieure conservée pour discussion, pas un accord ni une migration.
Le script de Lamia fera foi après validation.

| Élément proposé | Type / contrainte proposés |
|---|---|
| Table | public.adherents |
| id | bigint identity, clé primaire |
| email | varchar(254), NOT NULL, unicité sur la valeur normalisée |
| display_name | varchar(100), NOT NULL |
| password_hash | varchar(60), NOT NULL, BCrypt |
| role | varchar(16), NOT NULL, ADHERENT imposé à la création |

Confirmer noms, types, contraintes et identité générée. Ne pas figer un CHECK
ADHERENT définitif qui empêcherait les rôles d'un futur sprint.
Après réception : entité JPA, repository et adaptateur transactionnel AccountStore.
`create` doit imposer ADHERENT et traduire uniquement le conflit d'unicité email en
DuplicateEmailException, même sans pré-check, avec flush avant son retour pour
obtenir 409 dans l'API. Les autres erreurs SQL ne sont pas des doublons.
Aucune relation aux activités n'est ajoutée ici.
